# v0.1.4 Release Notes

`v0.1.4` 是在归档版 `v0.1.3` 之上整理出来的新版本。这个版本的重点不是新增一个孤立功能，而是把原来“云端 LLM + 语义跟踪 demo”推进成“支持本地 Qwen3、可做单卡分阶段执行、并具备更清晰规划/执行接口”的版本基线。

## 1. 版本定位

`v0.1.3` 更像一个稳定的语义跟踪与 LLM 任务分解演示版本。

`v0.1.4` 的目标是：

- 支持本地部署 `Qwen3`
- 支持 `OpenAI` 和本地 `Qwen3(vLLM)` 双后端
- 在单张 GPU 上通过 staged 模式完成“先规划、后执行”
- 把感知结果整理成 planner 可消费的结构化场景摘要
- 让 executor 的 step 执行更稳，不再直接拿旧目标继续追踪

一句话总结：

`v0.1.4` 把系统从“能演示”推进到了“更像一个分层式 VLA 雏形”。

## 2. 从 Pipeline 角度看发生了什么

### 2.1 v0.1.3 基线

```text
自然语言指令
  -> llm_task_planner_node
  -> /llm_task/plan_json
  -> llm_task_executor_node
  -> /sam3/prompt
  -> sam3_mask_node
  -> mask_depth_fusion_node
  -> iiwa_keypoint_tracker_node
  -> 机械臂执行
```

这个版本里：

- planner 基本固定走 `OpenAI Responses API`
- planner 基本只依赖用户指令，不消费更系统化的场景表
- executor 在 step 间切 prompt，但目标重确认逻辑还比较弱

### 2.2 v0.1.4 当前链路

```text
自然语言指令
  -> llm_task_planner_node
     -> OpenAI Responses API 或 本地 Qwen3(vLLM)
     -> 读取 /scene/objects_json 的场景摘要
  -> /llm_task/plan_json
  -> llm_task_executor_node
     -> 先发 prompt
     -> 等目标重新确认
     -> 再启用 tracking
  -> /sam3/prompt
  -> sam3_mask_node
  -> mask_depth_fusion_node
  -> scene_object_registry_node
  -> /scene/objects_json
  -> iiwa_keypoint_tracker_node
  -> 机械臂执行
```

和 `v0.1.3` 相比，新增的关键层是：

- 本地 Qwen3 推理服务层
- 感知到规划之间的 `scene_object_registry_node`
- executor 的 step 级目标确认层
- 单卡 GPU 资源调度层

## 3. 主要变化

### 3.1 LLM 后端从单一 OpenAI 变成双后端

现在 `llm_task_planner_node` 同时支持：

- `responses`
- `chat_completions`

这意味着原来只适用于 OpenAI 的 planner 位置，已经变成了一个可插拔推理后端接口。

对应代码：

- `src/pybullet_ros2_sim/pybullet_ros2_sim/llm_task_planner_node.py`
- `src/pybullet_ros2_sim/config/llm_task_planner_qwen3_vllm.yaml`
- `src/pybullet_ros2_sim/launch/llm_task_planner_qwen3_vllm.launch.py`
- `scripts/start_qwen3_vllm.sh`

### 3.2 planner 现在会利用场景摘要

`v0.1.3` 时 planner 主要面向“用户说了什么”。

`v0.1.4` 新增了：

- `scene_object_registry_node`
- `/scene/objects_json`
- `scene_registry_summary(...)`

这让 planner 不再只是纯语言分解器，而是开始读取“当前场景里看到了什么物体、它们是否可见、位置大概在哪”。

对应代码：

- `src/pybullet_ros2_sim/pybullet_ros2_sim/scene_object_registry_node.py`
- `src/pybullet_ros2_sim/pybullet_ros2_sim/task_plan_utils.py`
- `src/pybullet_ros2_sim/pybullet_ros2_sim/llm_task_planner_node.py`

### 3.3 executor 的 step 执行更稳

`v0.1.3` 的 executor 更接近：

- 发布 prompt
- 开启 tracking
- 满足条件后切下一步

`v0.1.4` 把它改成：

- 第一步先发 prompt
- 等感知侧确认“当前 step 的目标已经被重新锁定”
- 再打开 tracking

这能减少 step 切换时沿用旧 keypoint 的问题。

对应代码：

- `src/pybullet_ros2_sim/pybullet_ros2_sim/llm_task_executor_node.py`

### 3.4 感知链路做了时间对齐和稳健性增强

`mask_depth_fusion_node` 现在增加了：

- frame buffer
- 按时间戳找最接近的 color/depth/info
- 更清晰的状态日志

`sam3_mask_node` 现在：

- 直接把图像 header 跟着 mask 一起往下传
- 增加 prompt 与 score 的状态日志

这些改动的意义是让“语义提示 -> mask -> 3D keypoint”这一段更稳，减少因为异步时序抖动带来的无效目标。

对应代码：

- `src/perception_geometry/perception_geometry/mask_depth_fusion_node.py`
- `src/sam3_ros/sam3_ros/sam3_mask_node.py`

### 3.5 启动脚本从简单 launcher 变成资源编排器

`start_llm_rekep_demo.sh` 是这次变化最大的脚本之一。

相比 `v0.1.3`，现在它支持：

- `LLM_BACKEND=openai`
- `LLM_BACKEND=qwen3_local`
- `GPU_EXECUTION_MODE=concurrent`
- `GPU_EXECUTION_MODE=staged_single_gpu`
- `SIM_GUI=true/false`
- 检查和拉起本地 Qwen3
- 在 staged 模式下自动切换：
  - 停 SAM3
  - 起 Qwen3 做规划
  - 停 Qwen3
  - 起 SAM3 做执行

这部分是 `v0.1.4` 能在单卡机器上真正跑起来的关键。

对应代码：

- `start_llm_rekep_demo.sh`
- `start_llm_rekep_demo.local.example.sh`
- `clean_demo_processes.sh`
- `scripts/llm_task_cli.py`

## 4. 这个版本相对原有系统是“新增”还是“替换”

本次变化的一个重要特点是：

它主要是“插入新层”和“增强衔接”，不是把原有机器人链路推翻重写。

原有的：

- PyBullet 仿真
- SAM3 感知
- mask/depth fusion
- keypoint tracker
- iiwa 控制链路

都还在。

真正变化的是中上层：

- planner 后端从单一云模型扩展为双后端
- perception 与 planner 之间新增场景注册表
- executor 与 tracker 之间新增 step 级目标确认逻辑
- 启动层新增 GPU 资源调度逻辑

所以从架构关系上看：

- 原项目仍然是主体框架
- Qwen3 是嵌入进去的本地高层推理模块
- `scene_object_registry_node` 是这次补上的关键中间层

## 5. 为什么这个版本会更慢

当前速度变慢主要来自三部分：

- `staged_single_gpu` 模式下，每次任务都要在规划和感知执行之间切换 GPU 使用权
- executor 会等待目标重确认，再启用 tracking
- planner 和感知链路都更偏稳健配置，而不是极限低延迟配置

也就是说，`v0.1.4` 明确是“更稳、更完整”的版本，不是“最快”的版本。

## 6. 当前已知边界

虽然 `v0.1.4` 已经能形成更完整的闭环，但它还不是最终形态的完整 VLA：

- 动作集合仍然主要是 `hover_target` 和 `wait`
- Qwen3 仍然是高层语言规划器，不是多模态端到端 policy
- 单卡机器运行时，Qwen3 和 SAM3 仍然存在显存竞争
- staged 模式更适合 demo 和系统验证，不适合追求最低时延

## 7. 建议把 v0.1.4 理解成什么

建议把 `v0.1.4` 理解成：

- 一个新的稳定开发基线
- 一个本地大模型真正接入机器人仿真链路的版本
- 一个从“LLM planner demo”走向“分层式 VLA 框架”的过渡版本

后续如果继续演进，最自然的方向就是：

- 扩展动作集合
- 增强世界状态 schema
- 加入执行反馈驱动的重规划
- 逐步把这套系统推进成更完整的 VLA 架构
