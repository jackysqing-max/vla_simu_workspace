# Qwen3 融合进当前 VLA 框架的 Roadmap

这份 roadmap 的目标不是把 `Qwen3` 生硬地塞进系统里，而是把它放到最适合的位置，逐步把当前项目从“可用的 LLM planner”演进成“更完整、更稳的分层式 VLA 系统”。

## 1. 先明确 Qwen3 在这套系统里的角色

在当前项目里，`Qwen3` 更适合作为：

- 高层任务理解器
- 技能序列规划器
- 失败恢复时的重规划器
- 长时任务的语言记忆与约束管理器

`Qwen3` 目前不适合作为：

- 直接输入图像、直接输出关节控制的端到端 VLA policy
- 替代现有感知节点的视觉 backbone
- 替代低层控制器和 IK/跟踪逻辑

所以推荐路线不是“让 Qwen3 直接接管一切”，而是采用分层架构：

```text
感知层
  -> 结构化世界状态
  -> Qwen3 负责任务级规划与重规划
  -> 技能执行层
  -> 低层控制与机器人闭环
```

这是当前工程条件下最稳、最容易持续扩展的路线。

## 2. 当前基线状态

你现在已经有了一条最小闭环：

```text
/scene/objects_json
  -> llm_task_planner_node
  -> /llm_task/plan_json
  -> llm_task_executor_node
  -> 感知提示/目标跟踪/机械臂执行
```

当前基线的优点：

- 本地模型已经可用
- planner 与 executor 已经解耦
- 计划格式已经结构化 JSON 化
- 系统已经具备从“自然语言 -> 结构化步骤”的路径

当前基线的限制：

- 动作集合太小，目前只有 `hover_target` 和 `wait`
- 场景信息还偏轻量，世界状态表达还不够强
- 缺少执行反馈驱动的闭环重规划
- Qwen3 仍然是纯语言侧脑，不是多模态 VLA 本体
- 还没有系统化的数据记录和评测基线

## 3. 总体演进原则

后续推进时，建议一直坚持下面四条原则。

### 3.1 先分层，再统一

先把“感知、规划、执行、控制”之间的接口做稳，再考虑更强的一体化模型。否则问题会混在一起，很难定位。

### 3.2 先结构化状态，再追求更大模型

对机器人来说，结构化输入往往比盲目换更大模型更有效。一个好的世界状态表示，通常比从 `4B` 换到 `8B` 更能提升规划质量。

### 3.3 先提升闭环能力，再追求复杂任务

如果系统还不能可靠地处理“目标丢失、感知延迟、执行失败、对象不可见”，直接上长任务会非常脆弱。

### 3.4 让大模型负责语义与决策，不负责所有数值细节

高层决策交给 `Qwen3`，几何、IK、轨迹、安全约束仍然应该尽量放在确定性模块里。

## 4. 分阶段 Roadmap

下面给出一个更贴近当前代码结构的阶段划分。

## Phase 0: 稳定当前本地规划基线

### 目标

把“本地 Qwen3 规划链路”从一次性跑通，变成可以稳定复现、方便调试的基线。

### 需要完成的事

- 固化 `vLLM + Qwen3` 启动方式
- 固化 ROS2 `launch` 和参数文件
- 为 planner 增加更清晰的请求日志、响应日志和错误日志
- 为服务健康检查增加简单脚本或启动前检查
- 明确 fallback 触发条件，避免误把本地规则规划当成模型输出

### 重点文件

- `scripts/start_qwen3_vllm.sh`
- `src/pybullet_ros2_sim/config/llm_task_planner_qwen3_vllm.yaml`
- `src/pybullet_ros2_sim/pybullet_ros2_sim/llm_task_planner_node.py`

### 验收标准

- 连续多次重启都能稳定启动本地服务
- planner 对本地 Qwen3 的请求成功率高
- 能区分“模型规划成功”和“fallback 生效”
- 基础 demo 可重复演示

## Phase 1: 把场景输入升级成更强的结构化世界状态

### 目标

让 `Qwen3` 的输入不再只是松散文本，而是更稳定、更可约束的世界状态。

### 需要完成的事

- 给 `/scene/objects_json` 定义稳定 schema
- 每个对象至少包含：
  - `object_id`
  - `label`
  - `position`
  - `confidence`
  - `visible`
  - `timestamp`
  - 可选属性，如 `color`、`size`、`is_graspable`
- planner prompt 从“描述场景”升级为“读取状态表并做决策”
- 明确对象别名归一化逻辑，比如 `red cube`、`red block`、`cube_1`
- 记录最近几帧世界状态，避免单帧抖动导致计划不稳定

### 代码侧重点

- `scene_object_registry_node.py`
- `llm_task_planner_node.py`
- `task_plan_utils.py`

### 验收标准

- 同样的场景多次请求时，目标对象解析更稳定
- 规划结果里引用的对象名能映射回具体检测对象
- 感知小抖动不会频繁触发不同计划

## Phase 2: 从“悬停/等待”扩展到真正的技能规划

### 目标

让 planner 生成的内容更像机器人技能序列，而不是极简动作列表。

### 需要完成的事

- 扩展 plan schema，加入更多动作
- 推荐优先级：
  - `move_above`
  - `approach`
  - `grasp`
  - `lift`
  - `place`
  - `release`
  - `inspect`
  - `retry`
- 为每个动作增加前置条件和后置条件
- executor 从“逐条 prompt 驱动”升级为“技能状态机”
- 把高层动作和底层控制解耦：
  - Qwen3 只决定做什么
  - executor/skill layer 决定怎么做

### 代码侧重点

- `task_plan_utils.py`
- `llm_task_executor_node.py`
- 与 IK、抓取、跟踪、控制相关的执行节点

### 验收标准

- planner 输出的动作集合明显更贴近任务语义
- executor 可以稳定执行多步技能
- 不同技能之间有统一状态反馈，而不是散乱逻辑

## Phase 3: 加入执行反馈和闭环重规划

### 目标

让系统在执行中出错时，能够依靠 `Qwen3` 做重规划，而不是一旦失败就终止。

### 需要完成的事

- executor 发布结构化执行反馈
- 反馈内容至少包括：
  - 当前步骤
  - 成功/失败
  - 失败原因
  - 当前目标是否可见
  - 当前对象状态变化
- planner 支持输入：
  - 当前世界状态
  - 上一版计划
  - 已完成步骤
  - 失败原因
- 增加简单的 replanning policy：
  - 目标短时丢失时等待
  - 目标消失时重选目标
  - 操作失败时重试或回退
- 加入循环保护，避免“失败 -> 重规划 -> 同样失败”无限重复

### 建议新增接口

- `/llm_task/execution_feedback`
- `/llm_task/replan_request`
- `/llm_task/replan_status`

### 验收标准

- 常见失败场景下系统能自动恢复
- 重规划后的行为与失败原因一致
- 系统不会频繁进入死循环

## Phase 4: 形成分层式 VLA 架构

### 目标

把当前“LLM planner + executor”的形式，提升为更像 VLA 的分层系统。

### 推荐架构

```text
视觉感知/检测/跟踪
  -> 世界状态层
  -> Qwen3 任务规划层
  -> 技能层(skill layer)
  -> 低层控制层(IK/轨迹/控制器)
```

### Qwen3 在这一层的职责

- 解析任务目标
- 选择技能序列
- 维护任务上下文
- 根据执行反馈调整计划

### 不建议让 Qwen3 直接做的事

- 直接输出连续关节轨迹
- 直接输出高频控制量
- 替代视觉感知模型

### 如果后面想更接近真正的多模态 VLA

有两条路线可以选。

路线 A，推荐先做：

- 保留 `Qwen3` 作为高层大脑
- 感知层继续由现有检测/跟踪/视觉模块负责
- 通过结构化状态把视觉信息送给 Qwen3

路线 B，后续增强：

- 评估更强的多模态模型或专门的 VLA policy
- 让视觉表征直接进入高层决策
- 但依然保留 Qwen3 做任务管理和解释性规划

### 验收标准

- 高层计划、技能执行、低层控制边界清楚
- 任务复杂度提升后仍然能定位问题来源
- 模块替换成本低，比如后面更换感知模型或更换高层模型时不用重写整套系统

## Phase 5: 数据闭环、评测基线和模型升级

### 目标

让系统具备长期迭代能力，而不是只靠人工演示和手工调 prompt。

### 需要完成的事

- 记录任务级日志：
  - 用户指令
  - 世界状态
  - prompt
  - 模型输出
  - 执行轨迹
  - 最终结果
- 建立评测集：
  - 单步识别类任务
  - 多步操作类任务
  - 感知扰动类任务
  - 执行失败恢复类任务
- 定义核心指标：
  - 任务成功率
  - 规划延迟
  - 重规划次数
  - 首次成功率
  - 平均执行时长
- 在稳定基线上再评估：
  - `Qwen3-4B`
  - `Qwen3-8B`
  - 量化版本
  - 其他更适合本地部署的模型

### 验收标准

- 每次改动后都能量化比较优劣
- 模型升级不再只凭主观感受
- 能逐步形成适合你自己任务场景的数据闭环

## 5. 建议的优先顺序

如果按照“最快形成真实价值”的角度，我建议按这个顺序推进：

1. 先完成 Phase 0，稳定本地 Qwen3 规划基线。
2. 接着做 Phase 1，把世界状态结构化。
3. 然后做 Phase 2，扩展技能层和 plan schema。
4. 再做 Phase 3，加入失败恢复与重规划。
5. 最后进入 Phase 4 和 Phase 5，形成更完整的分层 VLA 和评测闭环。

这个顺序的好处是：

- 每一步都能单独验证
- 每一步都能直接带来可见收益
- 不会把“模型能力不足”和“系统接口设计不足”混为一谈

## 6. 一个现实建议

如果你的近期目标是“尽快让本地大模型在机器人系统里产生稳定价值”，那么最推荐的路线是：

`Qwen3 负责高层语义规划 + 现有感知负责视觉输入 + 技能层负责可执行动作 + 控制层负责确定性闭环`

这条路比“马上做统一端到端 VLA”更现实，也更适合当前这套代码基础。

## 7. 近期可以马上开工的具体事项

如果你想把 roadmap 变成接下来的开发清单，我建议先做这 5 件事：

1. 为 `/scene/objects_json` 固定 schema 和样例数据。
2. 为 `plan_json` 扩充动作定义和状态字段。
3. 给 executor 增加结构化执行反馈 topic。
4. 给 planner 增加“重规划模式”的输入模板。
5. 为 5 到 10 个典型桌面任务建立最小评测集。

这样做完之后，Qwen3 就不只是“本地跑起来了”，而会开始真正嵌进你的 VLA 框架。
